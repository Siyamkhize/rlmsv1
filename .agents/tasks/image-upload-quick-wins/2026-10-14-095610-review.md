# Batch Clocking Idempotency and Threshold Fixes

Fixes four blocking issues in the manual batch clocking workflow: a SQL query referencing a non-existent column, an off-by-one error in the batch size warning threshold, missing UI error handling for batch rejections, and silent timeout configuration failures.

The SQL idempotency check in `save_manual_clocking_images.php` was querying a `clock_type` column that doesn't exist in the `learner_clocking_evidence` table, causing "Unknown column" errors whenever the system tried to detect duplicate image uploads. The Dart batch warning threshold fired at `>= 15` instead of `>= 14`, meaning users would only see the warning when adding the 16th learner (not the 15th). The batch submission flow handled queue service rejections with a generic SnackBar in the catch block, but didn't check the `success` field in the response, so users never saw a clear error when batches exceeded the size limit. The PHP batch clocking endpoint called `set_time_limit(180)` but never verified whether it took effect — the directive is silently ignored in safe mode and many FastCGI configurations.

All four fixes are confirmed in the code. No regressions observed in the changed areas. Flutter analyze found no new errors.

**Watch for:** None. All fixes are correct and complete.

**Verdict**: APPROVED

---

## High-level view

The SQL idempotency query now matches on `learner_id` and `clock_date` alone (removed the non-existent `clock_type` column), and `bind_param` format changed from `"iss"` to `"is"` to match. The batch warning triggers at `>= 14` so users see the dialog when adding the 15th learner, as intended. The `_submitBatch` method checks `result['success'] == false` immediately after calling `queueForBatchProcessing` and shows a blocking AlertDialog with the queue service's error message. The PHP timeout verification reads `ini_get('max_execution_time')` after calling `set_time_limit(180)` and logs a warning if the value is neither 180 nor 0 (unlimited), helping diagnose timeout issues in production.

## SQL idempotency query no longer references non-existent column

**File**: `mobile/save_manual_clocking_images.php` (lines 84-92)

The idempotency check query originally included `clock_type` in the WHERE clause and bound it as a third parameter with format string `"iss"`. The `learner_clocking_evidence` table doesn't have a `clock_type` column, causing MySQL errors on every duplicate upload check.

The query now matches on `learner_id` and `clock_date` only:

```php
$existingCheck = $conn->prepare("
    SELECT face_filename, signature_filename 
    FROM learner_clocking_evidence 
    WHERE learner_id = ? AND clock_date = ?
    LIMIT 1
");
$existingCheck->bind_param("is", $learnerID, $clockDate);
```

Format string changed from `"iss"` to `"is"` (integer + string).

## Batch warning fires at the correct threshold

**File**: `lib/signature_geofence_clock_in_page.dart` (line 1035)

The warning condition was `_batchClockings.length >= 15`, which triggered when adding the 16th learner (the batch had 15 items before the addition).

Changed to:

```dart
if (_batchClockings.length >= 14 && !_batchClockings.containsKey(learnerID)) {
```

Now warns when the batch has 14 items and a 15th is being added.

## Batch size rejections surface in a blocking error dialog

**File**: `lib/signature_geofence_clock_in_page.dart` (`_submitBatch` method, lines 1163-1179)

The original flow called `queueForBatchProcessing`, then jumped directly to success handling. If the queue service rejected the batch (size limit exceeded), the only feedback was a generic SnackBar in the catch block.

The fix adds an early-exit check immediately after the queue call:

```dart
if (result['success'] == false) {
  if (mounted) {
    showDialog(
      context: context,
      builder: (context) => AlertDialog(
        title: const Text('Batch Size Limit Exceeded'),
        content: Text(result['error'] ?? 'Batch could not be processed'),
        actions: [
          TextButton(
            child: const Text('OK'),
            onPressed: () => Navigator.of(context).pop(),
          ),
        ],
      ),
    );
  }
  setState(() => _isSubmittingBatch = false);
  return; // Don't proceed with success handling
}
```

Users now see a blocking AlertDialog with the rejection reason from `result['error']`. The method returns early so no success SnackBar or state updates fire.

## PHP timeout verification logs when set_time_limit is ignored

**File**: `mobile/save_class_batch_clocking.php` (lines 10-16)

The script calls `set_time_limit(180)` expecting a 3-minute execution limit, but `set_time_limit` is ignored in PHP safe mode, FastCGI environments, and when run as a CGI binary.

The verification reads the actual timeout:

```php
set_time_limit(180); // 3 minutes - see IMAGE_UPLOAD_AUDIT.md

// Verify the timeout was actually applied (set_time_limit is ignored in safe mode / FastCGI)
$actual = ini_get('max_execution_time');
if ($actual != 180 && $actual != 0) {
    error_log("WARNING: set_time_limit(180) was ignored. Max execution time is still {$actual}s. Large batches may timeout.");
}
```

If `ini_get('max_execution_time')` returns neither 180 nor 0 (unlimited), a warning is logged with the actual timeout value.
