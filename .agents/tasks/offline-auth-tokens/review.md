# Offline authentication token persistence

Offline authentication now creates persistent sessions that survive app restarts. After successful bcrypt password verification, the system generates a cryptographically secure 64-character hex token, hashes it with SHA-256, and stores only the hash in a new SQLite `offline_sessions` table alongside user email, device ID, creation timestamp, and 7-day expiry. The plaintext token is stored in SharedPreferences. On app startup, the system validates the token against the stored hash and expiry, and auto-logs the user if still valid. Token refresh extends expiry during the last 24 hours. Logout clears both the database row and SharedPreferences.

**Watch for:** The `offline_sessions` table is created only in the migration path (v18), not in `onCreate`, so fresh installs will crash on first offline login (confirmed). Device binding is stored but never validated—a stolen token works on any device (likely). No audit trail exists for token operations, offline session abuse is invisible (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The token generation is cryptographically sound: 32 bytes from `Random.secure()`, hex-encoded to 64 characters, and only the SHA-256 hash is persisted. The plaintext token lives in SharedPreferences but never in the database. This matches industry standards for token-based auth.

Session expiry is enforced on every validation: expired tokens are auto-deleted from the database and SharedPreferences is cleared. The 7-day lifetime matches the online token behavior, and the optional refresh mechanism (enabled by default) extends sessions in the last 24 hours, providing a smooth UX without forcing re-login for active users.

The migration from memory-only sessions to persistent tokens runs cleanly for existing users upgrading from v17 to v18, but fresh installs on v18 won't have the `offline_sessions` table because `onCreate` doesn't create it. This breaks offline login immediately on new devices.

Device binding is cosmetic: the `device_id` column is populated from Android ID (or iOS identifierForVendor) and stored in the database, but `validateOfflineToken` never checks it. A token extracted from SharedPreferences on Device A will authenticate successfully on Device B if the database is copied or synced.

Backward compatibility is preserved: online authentication remains unchanged, and existing memory-only offline sessions degrade gracefully—they simply won't persist across restarts until the user logs in again and a token is created.

## Token generation uses Random.secure() and SHA-256 hashing

The `_generateSecureToken()` function produces a 64-character hex token from 32 bytes generated by Dart's `Random.secure()`, which uses the platform's CSPRNG (e.g., `/dev/urandom` on Android). This provides 256 bits of entropy, making brute force infeasible. The token is hashed with SHA-256 before storage:

```dart
Future<String> _generateSecureToken() async {
  final random = math.Random.secure();
  final bytes = List<int>.generate(32, (_) => random.nextInt(256));
  return bytes.map((b) => b.toRadixString(16).padLeft(2, '0')).join();
}

String _hashToken(String token) {
  return sha256.convert(utf8.encode(token)).toString();
}
```

The plaintext token is returned to the caller and stored in SharedPreferences (`offline_token`), but only the hash goes into the `offline_sessions` table. This prevents token recovery if an attacker gains read-only database access.

## offline_sessions table schema and indexing

The migration creates a new table at v18 with columns for user email (unique), token hash, device ID, creation timestamp, expiry timestamp, and last activity timestamp:

```sql
CREATE TABLE IF NOT EXISTS offline_sessions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_email TEXT NOT NULL UNIQUE,
  token_hash TEXT NOT NULL,
  device_id TEXT,
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL,
  last_activity_at TEXT NOT NULL
)
```

Two indexes are created: one on `user_email` for fast lookups during validation, and one on `expires_at` for potential future cleanup queries (though no cleanup routine currently uses it). The `UNIQUE` constraint on `user_email` ensures one session per user, preventing session proliferation. Inserting a new token uses `conflictAlgorithm: ConflictAlgorithm.replace`, which overwrites any existing session for that email.

The `device_id` column is nullable, so if device ID retrieval fails, the token is still created with `'unknown_device'` as the fallback.

## Migration runs for existing installs but onCreate omits the table

The v18 migration runs `CREATE TABLE IF NOT EXISTS offline_sessions` inside the `onUpgrade` callback when `oldVersion < 18`. Existing users upgrading from v17 (or earlier) will get the table automatically on next app launch. The migration is wrapped in a try-catch and logs errors, so a migration failure won't crash the app—it will just log `[DB] ❌ Error creating offline_sessions table: $e` and continue.

However, the `onCreate` callback—which runs only for fresh installs when no database file exists—does not create the `offline_sessions` table. It creates `users`, `facilitator`, `learnerdetails`, `province`, `district`, and others, but the offline_sessions table is missing. This means a user installing the app for the first time on v18 will have no `offline_sessions` table, and the first call to `createOfflineToken` will fail with a "no such table" error.

This is a critical bug. Fresh installs are broken for offline auth.

The fix is straightforward: add the `CREATE TABLE offline_sessions` SQL (and indexes) to the `onCreate` method, duplicating the migration logic.

## Device ID is stored but never validated

The `_getDeviceId()` function retrieves the Android ID (via `device_info_plus`) or iOS identifierForVendor and stores it in the `device_id` column during token creation. However, `validateOfflineToken` never reads or compares this column. It only checks `user_email`, `token_hash`, and `expires_at`.

```dart
// validateOfflineToken queries the session but ignores device_id
final result = await db.query(
  'offline_sessions',
  where: 'user_email = ?',
  whereArgs: [email],
);
// ... checks token_hash and expires_at, but device_id is never used
```

This means device binding is not enforced. If an attacker extracts the `offline_token` from SharedPreferences on Device A (e.g., via ADB backup, rooted device, or malware) and copies it to Device B, the token will validate successfully because the device check is missing.

Device binding enforcement would require:
1. Retrieve the current device ID in `validateOfflineToken`
2. Compare it to `session['device_id']`
3. Return false if they don't match

The current implementation provides no protection against token theft across devices. If the threat model includes physical device theft or credential sharing, this is a security gap. If the threat model assumes device security is sufficient (e.g., corporate-managed devices with encryption), this may be acceptable.

## Token expiry and auto-refresh logic

The 7-day expiry is calculated at token creation: `expiresAt = now.add(Duration(days: AppConfig.OFFLINE_SESSION_EXPIRY_DAYS))`. During validation, if `now.isAfter(expiresAt)`, the token is considered expired, the database row is deleted, and validation returns false. This prevents indefinite sessions.

The auto-refresh mechanism triggers when the remaining session lifetime is less than 24 hours. It extends the expiry by another 7 days from the current time:

```dart
final hoursUntilExpiry = expiresAt.difference(now).inHours;
if (AppConfig.OFFLINE_TOKEN_REFRESH_ENABLED && hoursUntilExpiry < 24) {
  final newExpiresAt = now.add(Duration(days: AppConfig.OFFLINE_SESSION_EXPIRY_DAYS));
  updateData['expires_at'] = newExpiresAt.toIso8601String();
  debugPrint('[OFFLINE_TOKEN] 🔄 Token refreshed for $email (new expiry: ${newExpiresAt.toIso8601String()})');
}
```

This creates a sliding window: active users who open the app within the last day of their session will get another 7 days without re-entering their password. Inactive users whose sessions lapse will need to log in again.

The refresh is conditional on `OFFLINE_TOKEN_REFRESH_ENABLED = true`, so the behavior can be disabled in config if required.

## Session restoration on app startup auto-logs users

The `_checkOfflineSession()` method runs during `initState` of the LoginPage. It reads `offline_token` and `offline_user_email` from SharedPreferences, loads the session from the database, validates the token, and navigates directly to the dashboard if valid:

```dart
final isValid = await dbHelper.validateOfflineToken(email, token);
if (!isValid) {
  await prefs.remove('offline_token');
  await prefs.remove('offline_user_email');
  return;
}
// ... fetch user details and navigate
_navigateBasedOnRole(role, classID, sdp, classData, learners, facilitatorId, classes, offlineData);
```

This provides the "Remember Me" UX: users who logged in offline and close the app will bypass the login screen on restart, as long as the token is still valid. The user never re-enters their password unless the token expires or they explicitly log out.

This is a deliberate UX tradeoff. The security implication is that password changes in the backend do not immediately invalidate offline sessions. If an admin resets a facilitator's password in MySQL, the bcrypt hash in the local SQLite database is unchanged, and the offline token remains valid until its 7-day expiry. The user won't be prompted for the new password until they attempt to sync online (which fails auth) or the offline token expires.

For systems with frequent password rotations or admin-driven revocations, this is a gap. A `password_updated_at` timestamp could be added to the `offline_sessions` table and checked during validation, but that requires backend coordination (syncing password change events).

## Logout clears both database and SharedPreferences

The `_logout()` function retrieves the user email from SharedPreferences, calls `clearOfflineSession(email)` to delete the database row, and then removes all session keys from SharedPreferences:

```dart
if (email != null) {
  await dbHelper.clearOfflineSession(email);
}
await prefs.remove('offline_token');
await prefs.remove('offline_user_email');
await prefs.remove('auth_token');
```

This ensures a clean logout: the token is invalidated in both storage locations, and auto-login won't trigger on next app launch. The `auth_token` removal also clears the online session token, so logout is comprehensive.

## Plaintext token in SharedPreferences is extractable

The plaintext token is stored in SharedPreferences with key `offline_token`. On Android, SharedPreferences files are located in `/data/data/<package>/shared_prefs/` and are readable by:
- Root access (rooted devices)
- ADB backup if the app manifest allows backup (which it does by default unless `android:allowBackup="false"`)
- Malware with root or debugging privileges

Once extracted, the token can be replayed on another device (because device binding isn't enforced) or used to authenticate as that user until expiry.

Mitigation options:
1. Use `EncryptedSharedPreferences` (Android) or Keychain (iOS) to encrypt the token at rest
2. Set `android:allowBackup="false"` in the manifest to prevent ADB extraction
3. Accept the risk if the threat model assumes physical device security

The current implementation opts for simplicity (SharedPreferences) over defense in depth. This is a common tradeoff in mobile apps targeting non-sensitive data or corporate-managed devices.

## SQL injection safety

All database queries use parameterized statements with `whereArgs`, so SQL injection is not possible even if the email contains special characters.

## Backward compatibility preserved

The online authentication path (via `login.php`) is untouched. The offline token is created in addition to the online flow, not as a replacement. Existing offline-only users (pre-v18) who had memory-only sessions will experience no disruption. On upgrade to v18, their next offline login will trigger `createOfflineToken`, and they'll gain session persistence.

The `getSdpByEmail` and `getFacilitatorByEmail` methods (which skip password verification) are new and only called during session restoration. They don't replace the existing `getSdp(email, password)` and `getFacilitator(email, password)` methods, so password verification is still enforced on initial login.

## No security logging or audit trail

Token creation, validation, expiry, and logout events are logged to the debug console (`debugPrint`) but not persisted. There's no database table or file log tracking:
- Which users created offline tokens and when
- How many validation attempts failed (wrong token, expired token)
- Whether tokens were validated from unexpected device IDs
- When tokens were explicitly cleared via logout vs auto-deleted due to expiry

This makes post-incident forensics difficult. If a user reports "someone accessed my account while I was offline," there's no evidence trail to confirm or deny token theft.

A simple security log table with columns `[event_type, user_email, device_id, timestamp, success, details]` would enable detection of:
- Brute force token guessing (multiple validation failures for one user)
- Replay attacks from different devices (device_id mismatch, if device binding is enforced)
- Abnormal token refresh patterns (refreshes at unusual intervals)

The lack of logging doesn't introduce a vulnerability, but it prevents detection and response.

## Test coverage gap

No automated tests exist for the offline token implementation. Error paths are handled conservatively: all async methods wrap database operations in try-catch and return `null` or `false` on error, with debug logging. If `createOfflineToken` fails due to a missing table, it logs the error and returns `null`, but the login flow continues—the user is logged in without a persistent session. This fail-open behavior is appropriate for offline use (login should succeed even if persistence fails), but it masks the onCreate bug until someone manually checks logs after a fresh install.
